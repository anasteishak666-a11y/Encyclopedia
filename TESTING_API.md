# Контракт API системы тестирования

Версия 1.0. Контракт для будущих Supabase Edge Functions и транзакционных PostgreSQL-функций. Источник правил — `TESTING_SPEC.md`; структура хранения — `supabase/migrations/002_testing_schema.sql`. Этот документ не включает реализацию.

## 1. Общие правила API

Базовый путь ниже условный: `/functions/v1/testing`. Формат запросов и ответов — JSON. Браузер передаёт `Authorization: Bearer <access_token>` от Supabase Auth и публичный ключ проекта по обычному механизму Supabase. Секретный ключ и доступ к схеме `private` остаются только на сервере. Сервер подтверждает токен, затем на **каждом** запросе проверяет `public.profiles.access_status = 'active'` и роль в `public.user_roles`. Сотрудник может проходить тесты и читать только свои данные; администратор выполняет только явно разрешённые административные операции. Идентификатор сотрудника не принимается от браузера для обычных операций: его берут из подтверждённой сессии.

Все идентификаторы в контракте — UUID. Временные метки передаются в ISO 8601 с UTC (`Z`). Сервер сам рассчитывает сроки и дополнительно возвращает готовые строки для показа по `Europe/Moscow`, например `19.10.2026 14:30 МСК`. Браузер может показывать обратный отсчёт, но не отправляет свой таймер, баллы, статус, начало, крайний срок или дату пересдачи как основание решения. `server_now` помогает отображению; окончательное решение всегда принимает сервер.

Успешные ответы не содержат полей `correct_option_ids`, `is_correct` или ключей вопросов полной аттестации. Единственное исключение — разрешённый разбор **своей завершённой базовой** попытки в операции результата. Сервер отдаёт только текущий вопрос, а не весь набор назначенных вопросов. Фотографии текущего вопроса выдаются как ограниченные для просмотра адреса или как публичные изображения энциклопедии; закрытый путь хранилища не служит ключом ответа.

Общий формат ошибки:

```json
{
  "error": {
    "code": "attempt_expired",
    "message": "Время теста истекло. Результат уже сохранён.",
    "retryable": false
  },
  "server_now": "2026-10-17T11:30:00Z"
}
```

`401` — нет действующей сессии; `403` — нет активного доступа или нужной роли; `404` — объект не существует **или принадлежит другому человеку**; `409` — состояние не позволяет действие; `422` — неверные входные данные; `503` — временная ошибка сервера либо банк не готов. Сообщения сотруднику не раскрывают чужие данные, ключи, внутренние SQL-ошибки и распределение закрытого банка. При сетевой ошибке браузер повторяет запрос с тем же идентификатором операции, а не предполагает успех или неуспех.

### Правила двух тестов

| Вид | Вопросы | Время | Проходной результат | После неуспеха |
| --- | ---: | ---: | ---: | --- |
| `basic` | 20 | 25 минут | 16 верных, 80% | Через 24 часа от завершения |
| `full` | 50 | 75 минут | 45 верных, 90% | Через 7 суток от завершения |

Успешный `basic` закрывается и открывает `full`. Для `full` подбор одновременно выполняет квоты тем `9/9/6/6/4/7/3/3/3` в порядке `private.topics.display_order` и сложностей `basic:15`, `medium:25`, `hard:10`. Успешная полная аттестация действительна три **календарных** месяца по `Europe/Moscow`: сохраняется число и местное время, а при отсутствии числа в целевом месяце берётся его последний день. После неуспешной переаттестации статус — `attestation_not_confirmed`, новая попытка подчиняется семи суткам. Сервер хранит события в UTC и возвращает рассчитанные сроки. Уровни знания: менее 60% — `insufficient`, 60–79% — `basic`, 80–89% — `good`, от 90% — `excellent`. Уровень и факт прохождения — разные поля.

Целевой объём банков — примерно 50 вопросов `basic` и 150 вопросов `full`; это не повод ослаблять квоты или включать непроверенные вопросы. Допустимые типы соответствуют схеме: `single`, `multiple`, `scenario_single`, `scenario_multiple`, `photo_single`, `photo_multiple`. Свободных текстовых ответов нет.

## 2. Доступные тесты и сроки

`GET /tests/availability`

**Браузер отправляет:** только токен. Параметры времени, сотрудника или результата не принимаются.

**Сервер возвращает:**

```json
{
  "server_now": "2026-10-17T11:00:00Z",
  "tests": [
    {
      "kind": "basic",
      "state": "passed",
      "can_start": false,
      "reason": "basic_already_passed",
      "active_attempt_id": null,
      "next_allowed_at": null,
      "next_allowed_moscow": null
    },
    {
      "kind": "full",
      "state": "available",
      "can_start": true,
      "reason": null,
      "active_attempt_id": null,
      "next_allowed_at": null,
      "next_allowed_moscow": null
    }
  ],
  "attestation": {
    "status": "not_started",
    "valid_until": null,
    "valid_until_moscow": null
  }
}
```

`state`: `available`, `in_progress`, `cooldown`, `prerequisite_required`, `passed`, `valid_until_due`, `bank_unavailable`. При открытой попытке возвращаются `active_attempt_id` и серверный `deadline_at`. `next_allowed_at` задаётся только сервером; досрочное разрешение может открыть пересдачу раньше. Пока полная аттестация действительна, повторное прохождение не открывается без допустимого административного разрешения. Для отключённого сотрудника ответ — `403`.

**Проверки:** активный профиль, роль `employee`, последний завершённый результат, открытая попытка, срок пересдачи, успешность базового теста, действительность аттестации, доступность проверенного банка.

**Ошибки и повторы:** `401`, `403`, `503`. Повторный `GET` ничего не создаёт и может вернуть обновившиеся сроки или состояние.

## 3. Запуск или восстановление попытки

`POST /attempts/start-or-resume`

**Браузер отправляет:**

```json
{ "kind": "full" }
```

**Сервер возвращает:**

```json
{
  "attempt": {
    "id": "uuid",
    "kind": "full",
    "state": "in_progress",
    "question_count": 50,
    "answered_count": 0,
    "started_at": "2026-10-17T11:00:00Z",
    "deadline_at": "2026-10-17T12:15:00Z"
  },
  "resumed": false,
  "server_now": "2026-10-17T11:00:00Z",
  "current_question_url": "/attempts/uuid/current-question"
}
```

Если уже есть незавершённая попытка того же вида, сервер возвращает **её** с `resumed: true`, сохранённым порядком и фактическим оставшимся временем. Если её срок истёк, сервер сначала завершает её и возвращает `409 attempt_expired` со ссылкой на результат; новую попытку тем же запросом не создаёт.

**Проверки:** подтверждённый активный сотрудник; отсутствие одновременно запущенной попытки другого вида; для `full` — успешный `basic`; отсутствие запрета по успешному результату или паузе пересдачи; неиспользованное досрочное разрешение при необходимости. В одной транзакции и под блокировкой на сотрудника выбирается текущая версия активных, полных вопросов, проверяется достаточность банка, соблюдаются **обе** квоты полной аттестации, предпочитаются ещё не встречавшиеся вопросы, фиксируются случайный порядок вопросов и вариантов в `attempt_questions` и `attempt_question_options`. `started_at` и `deadline_at` устанавливает база по версии `test_rules`. При недостатке подходящих вопросов запуск полностью откатывается.

**Ошибки и повторы:** `409 prerequisite_required`, `cooldown_active`, `already_passed`, `attestation_not_due`, `another_attempt_in_progress`, `attempt_expired`; `503 bank_unavailable`. Одновременные и повторные запросы не создают два открытых теста: помогают транзакционная блокировка и индекс `one_open_attempt_per_test`. Повтор после успешного запуска возвращает ту же открытую попытку.

## 4. Текущий вопрос

`GET /attempts/{attempt_id}/current-question`

**Браузер отправляет:** только `attempt_id` в пути и токен.

**Сервер возвращает:**

```json
{
  "attempt_id": "uuid",
  "position": 7,
  "question_count": 50,
  "question": {
    "attempt_question_id": "uuid",
    "type": "photo_multiple",
    "prompt": "Формулировка вопроса",
    "topic": "Фото на фотофоне",
    "photos": [{ "url": "https://...", "caption": "Снимок А" }],
    "options": [
      { "id": "uuid", "label": "Вариант А" },
      { "id": "uuid", "label": "Вариант Б" }
    ]
  },
  "deadline_at": "2026-10-17T12:15:00Z",
  "server_now": "2026-10-17T11:13:10Z",
  "remaining_seconds": 3710
}
```

`remaining_seconds` — подсказка для отображения, рассчитанная сервером; право ответить проверяется заново при отправке. Сервер выдаёт лишь первый вопрос без подтверждённого ответа. Назначенные номера и порядок вариантов не пересоздаются после обновления страницы.

**Проверки:** активный сотрудник, владение попыткой, состояние и крайний срок. `404` скрывает существование чужой попытки; при истечении срока сервер завершает её и возвращает `409 attempt_expired` с адресом результата. После завершения — `409 attempt_finished`. Повторный `GET` не меняет порядок и не открывает следующий вопрос без сохранённого ответа.

## 5. Подтверждение ответа

`POST /attempts/{attempt_id}/answers`

**Браузер отправляет:**

```json
{
  "request_id": "uuid",
  "attempt_question_id": "uuid",
  "selected_option_ids": ["uuid", "uuid"]
}
```

`request_id` создаётся браузером для **одного подтверждения** и сохраняется до ответа сервера. Массив содержит уникальные идентификаторы предъявленных вариантов; пустой массив не принимается. Браузер не отправляет правильность, балл или время.

**Сервер возвращает:**

```json
{
  "saved": true,
  "already_saved": false,
  "request_id": "uuid",
  "attempt_question_id": "uuid",
  "answered_count": 7,
  "attempt_state": "in_progress",
  "server_now": "2026-10-17T11:13:12Z",
  "next_question_url": "/attempts/uuid/current-question",
  "result_url": null
}
```

**Проверки:** активный владелец, открытая попытка, серверный срок, именно первый неотвеченный вопрос, допустимое количество и принадлежность выбранных вариантов этому вопросу. В одной транзакции под блокировкой попытки сервер сравнивает **множества** выбранных вариантов с `private.answer_keys`, записывает один `attempt_answers` и его `attempt_answer_selections`. Частичных баллов нет. Правильность и ключи не входят в ответ. Последний подтверждённый ответ в той же транзакции завершает попытку; тогда `attempt_state: "completed"`, `next_question_url: null`, `result_url` заполнен.

**Ошибки и повторы:** `422 invalid_options`; `409 question_out_of_order`, `answer_locked`, `attempt_expired`, `attempt_finished`, `request_id_conflict`. Для владельца сервер **сначала** ищет уже сохранённый ответ: повтор с тем же `request_id` и тем же набором или с новым `request_id`, но **тем же уже сохранённым набором** возвращает подтверждение с `already_saved: true`, в том числе после завершения попытки. Для последнего ответа возвращается `result_url`. Другой набор никогда не заменяет ответ. Лишь если подтверждения нет, проверяется истечение срока; просроченный неподтверждённый ответ не записывается. Уникальность `attempt_answers.attempt_question_id` и `request_id` дополняет проверку в транзакции. Клиент после сетевой ошибки повторяет прежний запрос и ждёт подтверждения.

## 6. Завершение попытки

`POST /attempts/{attempt_id}/finish`

**Браузер отправляет:** только токен и `attempt_id`; тело `{}`. Это запрос синхронизации состояния, **не** способ закончить тест досрочно или передать итог.

**Сервер возвращает:**

```json
{
  "attempt_id": "uuid",
  "state": "completed",
  "finished_at": "2026-10-17T12:00:00Z",
  "result_url": "/attempts/uuid/result",
  "server_now": "2026-10-17T12:00:00Z"
}
```

Сервер сам вызывает ту же транзакционную операцию после последнего ответа и по истечении `deadline_at`. Фоновое задание завершает просроченные попытки, даже если браузер закрыт. Любое чтение или отправка ответа также сначала проверяет срок. При тайм-ауте неотвеченные вопросы дают 0 баллов; `state = timed_out`.

**Проверки:** активный владелец; истёкшее время **или** все назначенные ответы подтверждены. Сервер считает количество правильных ответов из сохранённых `is_correct`, процент и уровень, результаты по темам, `retry_available_at` либо `valid_until` в московском календаре. Затем один раз сохраняет `attempt_results` и `attempt_topic_results` и переводит попытку в окончательное состояние в одной транзакции.

**Ошибки и повторы:** `404` для чужой попытки; `409 attempt_incomplete`, если время ещё есть и ответы остались. Повтор для завершённой попытки возвращает прежний `result_url` без повторного подсчёта и начисления. Блокировка строки, первичный ключ `attempt_results.attempt_id` и неизменяемые триггеры защищают итог от дублей.

## 7. Результат и история

`GET /attempts/{attempt_id}/result` и `GET /attempts/history`

**Браузер отправляет:** токен и, для результата, `attempt_id`. История может принять `limit` и непрозрачный `cursor`; фильтр по чужому `employee_id` у сотрудника отсутствует.

**Результат полной аттестации:** `kind`, время, состояние, `correct_count`, `question_count`, общий `percentage`, `knowledge_level`, `passed`, `outcome`, рассчитанные сервером `retry_available_at`/`valid_until` и московские строки, массив из девяти `{topic, correct_count, question_count, percentage}`, рекомендации `{topic, encyclopedia_href}` **только** для тем с результатом ниже 80%. Нет отдельных вопросов, выбранных или правильных вариантов, объяснений, `is_correct`, `answer_keys` и сведений, позволяющих восстановить ключ.

**Результат базового теста:** тот же общий итог. Только для **своей завершённой базовой попытки** (`completed` или `timed_out`) возвращается `review` из всех 20 вопросов в порядке попытки. Каждый элемент содержит `position`, `prompt`, показанные `options` в сохранённом порядке, `answered`, `selected_option_ids`, `correct_option_ids` и короткое `explanation_text` (может быть `null` у старых версий). Для неотвеченного вопроса `answered = false` и `selected_option_ids = []`. Разбор не содержит вопросов, ключей или объяснений полной аттестации.

До завершения попытки запрос результата возвращает `409 result_pending` без разбора. Если серверный срок уже истёк, сервер сначала завершает попытку и только затем выдаёт результат. Административный маршрут `GET /admin/attempts/{attempt_id}/result` возвращает сводку без `review`, правильных ответов и объяснений, включая базовый тест. Ответы на запросы текущего вопроса, сохранения ответа, завершения и истории также не содержат ключей или объяснений.

**История:** список завершённых попыток с видом, временем, процентом, уровнем и статусом; для `full` — также проценты по темам. Отдельно `latest` и `best` по каждому виду теста. Активная попытка показывается через операцию доступности. Административный обзор истории использует отдельный серверный маршрут с проверкой `admin` и возвращает те же безопасные сводки без ответов полной аттестации.

**Проверки:** активный сотрудник и владение попыткой; для администратора — отдельная проверка роли. `404` скрывает чужую попытку; `409 result_pending` означает, что она ещё не завершена; `401`/`403` — отсутствие доступа. Повторный `GET` завершённой попытки не меняет данные. История сохраняется после отключения доступа и вновь доступна после его восстановления; удаление персональных данных выполняется отдельной будущей операцией.

## 8. Административное разрешение досрочной пересдачи

`POST /admin/retake-overrides`

**Браузер администратора отправляет:**

```json
{
  "request_id": "uuid",
  "employee_id": "uuid",
  "kind": "full",
  "note": "Краткая причина"
}
```

**Сервер возвращает:** `{ "override_id": "uuid", "employee_id": "uuid", "kind": "full", "granted_at": "2026-10-17T11:00:00Z", "used_by_attempt_id": null }`. Действие записывается в `private.retake_overrides` с подтверждённым `granted_by`. Оно открывает **одну будущую попытку** раньше паузы после неуспеха либо срока переаттестации; не сбрасывает успешный базовый тест и не меняет прежнюю историю.

**Проверки:** активный `admin`; существующий активный сотрудник роли `employee`; непустая причина длиной до 500 символов (оценку уважительности делает администратор); выбранный тест и серверное состояние `cooldown` либо `valid_until_due`; отсутствие уже неиспользованного разрешения этого вида. Отключённому сотруднику разрешение не выдаётся, пока доступ не восстановлен. При запуске попытки сервер атомарно помечает разрешение использованным в `used_by_attempt_id`, проверяя того же сотрудника и вид теста. Обычные сроки пересдачи не меняются.

**Ошибки и повторы:** `403 admin_required`; `404 employee_not_found`; `409 override_not_needed`, `override_already_open`; `422 invalid_kind`/`invalid_note`. Повтор с тем же `request_id` возвращает прежнее разрешение. Два одновременных запроса сериализуются блокировкой сотрудника.

**Дополнение к схеме до реализации:** в миграции `002` у `retake_overrides` нет `request_id` и уникального ограничения на одно неиспользованное разрешение для пары `(employee_id, test_kind)`. Следующая миграция должна добавить их, чтобы описанная идемпотентность оставалась гарантированной после перезапуска сервера. До этого административный маршрут нельзя включать в работу.

## 9. Управление сотрудниками

**Управление ФИО (после миграции 008):** `POST /admin/employees/{employee_id}/name` принимает обязательные `first_name` и `last_name` (по 1–100 символов после обрезки пробелов), возвращает `employee_id`, `first_name`, `last_name`. Меняется только профиль существующего сотрудника; UUID, роль и история не меняются. Edge Function и SQL-функция проверяют активного администратора.

**Приглашение (после обновления Edge Function):** `POST /admin/employees/invite` принимает `email`, `first_name`, `last_name`, `redirect_to`. Сервер проверяет администратора и адрес возврата, отправляет приглашение через Supabase Auth Admin с именем и фамилией в метаданных. Триггер из миграции 001 создаёт профиль и роль сотрудника после подтверждения email. Приглашённый появится в `GET /admin/employees` после подтверждения адреса.

## 10. Границы реализации и приёмка

PostgreSQL-функции выполняют атомарные операции с блокировкой строк, подбор по квотам, чтение закрытых ключей, фиксацию ответов, финализацию, московскую календарную арифметику и проверку разрешений. Edge Functions проверяют Auth, валидируют форму запроса, вызывают доверенные функции базы и формируют **явно перечисленные** выше поля ответа. Они не делают последовательность отдельных записей, от которой зависит целостность попытки. Схема `private` не добавляется в Supabase Exposed schemas; браузер не получает прямых прав на её таблицы.

До подключения интерфейса проверяются: конкурентный запуск, точные квоты и нехватка банка, неизменность порядка после обновления, тайм-аут при закрытом браузере, повтор и конфликт ответа, немедленное завершение после последнего ответа, сроки 24 часа/7 суток/3 календарных месяца (включая 31 января → 30 апреля), отсутствие чужих данных и ключей полной аттестации в каждом ответе API. Демонстрационные данные заменяются лишь после готовности серверных операций и проверенного банка.
